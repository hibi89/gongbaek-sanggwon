작성 기준일: 2026-10-01 · 목표 상품: 주소 1곳, 79,000원

## 0. 현재 상태

기존 루트 `배달상권분석.json`은 주소 검색과 좌표 생성 뒤 업종별 반경 API를 호출하도록 구성돼 있다. `Category List`에는 코드 247개가 들어 있으나 기존 실행 흐름은 아래와 같다.

1. `Food Categories`가 `I2` 코드만 통과시킨다.
2. `First Category` 코드가 그중 첫 업종 하나만 다음 단계로 보낸다.
3. `Generate Pages`가 `First Category` 노드를 다시 참조한다.
4. `Generate Pages`에는 `pageSize = 1000`이 고정돼 있고, 운영상 최대 페이지 크기인지 확인되지 않았다.
5. `Flatten Stores`는 응답의 `body.items`를 펼치지만 점포 거리 계산, 중복 제거, 업종별 집계, TOP20 순위는 하지 않는다.

저장된 기존 workflow 실행결과로 247개 전체 분석을 증명할 수 없다. 따라서 판매 처리에는 새 V1 파일을 사용한다. 원본은 이전 구현의 참조용으로 둔다.

## 2. V1 데이터 경로: 전국 CSV 스냅샷 — 확정

V1은 소상공인시장진흥공단 전국 상가정보 CSV 한 벌을 기준으로 사용한다. 2026-09-30 확인 시 공식 페이지의 최신 배포본은 `20260630` 기준 파일이었다. 최신 파일이 교체되면 **실제 다운로드한 기준일**을 기준으로 새 snapshot을 만들며 이 날짜를 고정값으로 사용하지 않는다. [공식 CSV 안내](https://www.data.go.kr/data/15083033/fileData.do)

CSV를 한 번 정규화해 두고, 주문마다 분석 기준점 5km 안의 자료만 Python/DB에서 질의한다. 전국 점포 전체를 n8n item stream으로 보내지 않는다. 기준일이 다른 API 응답을 CSV snapshot에 섞지 않아 두 순위가 같은 시점 자료를 쓰게 한다.

```text
공식 전국 파일 확인
→ 기준일·출처·checksum 기록
→ 원본 보존
→ 공통 점포 필드로 정규화
→ 코드·좌표·ID 확인
→ 검증된 스냅샷으로 저장
→ 요청 주소의 5km 점포만 가져오기
```

### 로컬 실행 연결

```text
로컬 n8n: Analysis Input 노드에 주소 입력·좌표 확인·request_id 생성
→ 로컬 Python 분석기: 정규화 snapshot에서 분석
→ 결과 JSON 반환
→ n8n: 결과·상태 저장 및 후속 리포트 처리
```

Python 분석기는 snapshot을 읽고 계산한 결과만 반환한다. `scripts/start_analyzer.ps1`은 서비스 bearer token을 `%LOCALAPPDATA%\GapAnalysis\analyzer-token.txt`에 보관한다. 첫 실행 화면에는 token 자체를 출력하지 않고, 사용자가 로컬 파일에서 직접 복사하도록 안내한다. n8n에는 두 개의 `HTTP Header Auth` credential을 만든다: Kakao 주소검색용(`Authorization: KakaoAK ...`)과 분석기용(`Authorization: Bearer ...`). 둘 다 workflow JSON이나 채팅에 넣지 않는다.

새 workflow의 `Analysis Input`은 설명용 문구로 시작한다. 실제 실행 전 요청 주소로 바꾸며 `Validate Analysis Input`이 placeholder 상태면 주소검색 전에 중단한다. 기본 analyzer URL `127.0.0.1:8765`는 n8n 네이티브 설치 기준이다. Docker 설치라면 컨테이너에서 Windows host로 통신하도록 URL과 bind 구성을 조정한 뒤 실행한다. Docker 여부를 확인하기 전까지 loopback URL을 Docker에서도 된다고 가정하지 않는다.

### API의 역할: V2 또는 보조 검증

기존 반경 API 노드는 V1 전수분석 입력으로 쓰지 않는다. API는 향후 최신성 기능(V2)을 검토하거나, 개발 중 표본 주소의 수치를 비교하는 보조 검증용으로 남긴다. 보조 확인 결과를 V1 snapshot 결과에 합치지는 않는다.

- 특정 API 결과를 제품 자료에 쓰기로 별도 결정한다면, 해당 시점의 공식 명세로 코드 전체 지원·페이지 크기·응답 건수·요청 제한을 먼저 확인하고 이 문서의 V2 API 품질 게이트를 적용한다.

API 키는 워크플로우 JSON에 직접 기록하지 말고 n8n credentials로 관리한다. 구버전 루트 JSON의 정적 Kakao Authorization 값은 제거했고, 해당 노드는 HTTP Header Auth를 요구하도록 바꿨다. 새 JSON도 인증값을 포함하지 않는다. 이전 값은 프로젝트 검토 중 노출됐을 수 있으므로 실제 Kakao 운영 키는 개발자 콘솔에서 교체한 뒤 n8n credential에 등록한다.

## 3. 공통 데이터와 거리 계산

최소 공통 필드는 다음과 같다.

| 필드 | 용도 |
|---|---|
| `snapshot_id`, `source_as_of` | 원자료 버전·기준일 추적 |
| `source_store_id` | 페이지 재수집 중복 제거 |
| `category_code`, `category_name` | 업종별 집계 |
| `longitude`, `latitude` | 거리 계산 |
| `source_row` 또는 원본 JSON | 문제 조사와 재현 |

분석 요청에는 `request_id`(고객 표시용 분석번호), 입력주소, 정규화 주소, 기준 좌표, `snapshot_id`, 분류표 버전, 분석엔진 버전을 함께 기록한다. 전국 자료가 크면 PostgreSQL/PostGIS에 스냅샷과 공간 인덱스를 저장한다. 파일럿에서는 검증된 Parquet/CSV와 Python 분석기로 시작해도 된다.

점포별 기준 좌표까지의 거리를 미터로 계산한 뒤 1/2/3/4/5km 누적 count를 만든다. 경계 포함 규칙은 `거리 ≤ 반경`으로 통일한다. 동일 점포 ID가 페이지 간 반복된 경우 같은 스냅샷에서 중복 집계하지 않는다. 주소·상호가 비슷하다는 이유만으로 별도 점포를 병합하지 않는다.

## 4. Python/Pandas 분석

분석 입력 예시:

```json
{
  "request_id": "...",
  "snapshot_id": "...",
  "center": {"lon": 129.0, "lat": 35.0, "crs": "EPSG:4326"},
  "radii_m": [1000, 2000, 3000, 4000, 5000],
  "taxonomy_version": "...",
  "analysis_engine_version": "..."
}
```

분석 순서:

1. 좌표·코드·자료 버전 검사.
2. 유효 ID로 중복 제거하고 제거 수를 저장.
3. 정확한 거리(m)를 계산하고 반경 밖 점포를 제거.
4. 업종별로 `N_1km`, `N_2km`, `N_3km`, `N_4km`, `N_5km`를 계산.
5. 내부 저장용 구간별 신규 점포 수도 차이로 계산: `0~1=N1`, `1~2=N2-N1`, ..., `4~5=N5-N4`. V1 리포트에는 포함하지 않는다.
6. 전수 조회된 활성 업종 코드표를 기준으로 count 0 업종도 결과 테이블에 명시적으로 생성.
7. 전체 검증 업종을 `[N_5km, N_4km, N_3km, N_2km, N_1km, category_code]` 오름차순 정렬 후 20개 선택.
8. 같은 집계 결과에서 A 태그 업종만 추린 뒤 동일한 키로 오름차순 정렬해 10개 선택.
9. 두 목록에 코드·업종명·A/B/C 참고 태그와 5개 누적 count를 붙임. 두 결과 목록의 중복은 허용.
10. 분석 완료 상태, 기준일, 분류표 버전, 분석엔진 버전, 오류와 미분류 수를 함께 반환.

구간별 밀도·시장수요 점수·점포 비중 등은 이번 단일 상품 계산에 포함하지 않는다. 결과 필드를 고객에게 설명 가능한 수준으로 유지한다.

## 5. n8n 역할과 결과 품질 게이트

n8n은 주문 입력과 주소 확인, 분석 요청 ID 발급, 전체 스냅샷/반경 데이터 선택, Python 실행, 진행 상태 추적, 결과 전달을 담당한다. 대규모 데이터 집계와 순위 계산은 Python 또는 DB에서 수행한다.

### 두 수집 방식 공통 게이트

- 주소 검색 결과와 기준 좌표가 정상.
- 분류표 버전과 원자료 기준일이 있음.
- 상품에 표기할 분석 대상 코드의 공식 매핑과 데이터 지원 여부가 확인됨.
- 오류·미지원·좌표 결측을 정상 0 count로 처리하지 않음.
- 점포 중복 제거와 업종별 합계가 재현 가능.
- 누적 count가 `N1 ≤ N2 ≤ N3 ≤ N4 ≤ N5`를 만족.
- TOP20 정렬이 정해진 우선순위와 일치.
- A 태그 매핑이 확정된 분류표 버전이며 A TOP10이 같은 정렬 함수를 사용.
- 검증된 현재·지원 A 업종이 10개 미만이면 상품 설정을 `blocked`로 두고 출시 및 리포트 발행을 중단한다. 10개 미만의 목록을 TOP10으로 대체하지 않는다.
- 경계 29개 중 운영자 결정이 없거나 보류가 남아 있으면 taxonomy 최종 승인과 전체 상품 리포트 발행을 중단한다.
- 0건은 선택한 수집 방식에서 전체 데이터 처리가 완료된 업종 코드에만 표시.
- 고객 결과에 출처와 자료 기준일, 안내 문구가 들어 있음.

### 전국 파일 스냅샷 방식 전용 게이트

- 공식 배포 파일과 메타데이터를 기록하고 다운로드가 완료됨.
- 파일 크기·체크섬 또는 동등한 무결성 확인을 통과함.
- 전체 파일 파싱 행 수와 적재 행 수가 일치하고, schema/type 오류가 처리됨.
- 좌표 정규화·ID 중복 처리·taxonomy 매핑이 끝나고 미분류/미지원 건수가 명시됨.
- 스냅샷이 `complete` 상태로 승격된 경우에만 0건 판단과 분석을 허용함.
- 파일 방식에는 API 페이지 완료 조건을 적용하지 않는다.

### 반경 API 방식 전용 게이트 — V2/보조 확인에만 적용

- 전체 대상 업종 코드별 응답 상태를 기록하고 모든 예정 페이지를 성공적으로 수신함.
- API/provider 응답코드와 업종별 total count를 확인하고 수신 행 수와 대조함.
- 누락·실패 페이지, 지원하지 않는 코드, 재시도 중복을 manifest에 기록함.
- 정상 0건은 해당 업종의 성공 응답과 `totalCount=0` 등 명시적인 빈 결과가 확인된 경우만 인정함.
- API 방식에는 전국 파일 checksum·전체파일 파싱 행 수 조건을 적용하지 않는다.

어느 방식이든 해당 방식의 품질 게이트를 만족하지 않으면 완성 리포트를 내지 않고 `incomplete` 또는 `failed` 상태로 남긴다.
