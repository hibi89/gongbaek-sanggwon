## 현재 확인된 실행 상태

- n8n은 `http://127.0.0.1:5678`에서 응답한다.
- 분석기는 `http://127.0.0.1:8765/health`에 HTTP 200과 `ready`를 반환한다. 현재 서비스 응답은 확인했으며 소켓 소유 PID는 별도 확인되지 않았다.
- 현재 분석기 DB와 taxonomy는 `semas-20260630-taxonomy-v3-abc-6048205a8203-sha256-2fba22711d8fb289`으로 일치한다. 정식 SHA-256은 `2fba22711d8fb28916546c475168da64f1af1a6c06bdf64abfd199566adb9ed0`이다.
- analyzer bearer token은 프로젝트 밖 `%LOCALAPPDATA%\GapAnalysis\analyzer-token.txt`에 저장되며 콘솔·저장소·workflow JSON에 출력하지 않는다.
- 공유용 V1 workflow JSON은 7개 노드이며 credential secret이 없고 Analysis Input은 placeholder다. 로컬 n8n에는 Kakao와 analyzer credential이 연결되어 있다.
- Kakao 검색 결과가 정확히 1건일 때만 다음 노드로 진행하고 최종 publication gate에서도 매치 수 1건을 다시 확인한다. 두 조건은 로컬 n8n workflow에 저장되어 있다.
- 공개 시설 주소 5곳에서 전체 7개 노드 live E2E를 수행했다. execution 273~277 모두 Kakao/analyzer HTTP 200, 247개 분류, TOP20 20행/A TOP10 10행, publication gate 통과였고, 각각 read-only 납품 검증도 통과했다. 주소 입력은 테스트 후 실행 전 원래 설정으로 복원했다. 상세 결과는 `검증/20261001_신뢰성_검수결과.md`.
- 2026-10-01 추가 live 실패 확인: execution 278 analyzer 연결 거부, execution 280 publication gate blocked. 시험 뒤 Analysis Input placeholder, 운영 analyzer URL, 빈 Analyzer pinData를 saved workflow DB에서 확인했다.

## 고정 실행환경

- 검증된 버전: CPython 3.12.14, Node.js 24.21.0, n8n 2.40.7. analyzer 시작 스크립트가 `.venv` 또는 정확히 핀된 인터프리터만 받아들이며, 실제 재기동에서 Python 3.12.14를 확인했다.
- Python 버전은 `.python-version`, Python 패키지는 `requirements.lock`, Node.js는 `.nvmrc`, n8n은 `n8n-version.txt`에 고정했다.
- `scripts/start_n8n_with_retention.ps1`은 n8n과 Node.js 버전이 고정값과 다르면 실행을 중단한다.
- 새 PC에서는 Python 3.12.14를 설치한 뒤 아래처럼 가상환경을 만들고 잠금 파일을 설치한다.

  ```powershell
  py -3.12 -m venv .venv
  .\.venv\Scripts\python.exe -m pip install -r requirements.lock
  .\.venv\Scripts\python.exe --version
  ```

- 출력 Python 버전이 `3.12.14`가 아니면 운영 분석을 시작하지 않는다.

## 운영 n8n 시작 절차 — 전용 스크립트만 사용

- 운영 n8n의 시작·재시작은 프로젝트 루트에서 `./scripts/start_n8n_with_retention.ps1`만 사용한다. PowerShell에서는 `./` 대신 `.`으로 입력해도 된다.
- 이 스크립트가 n8n/Node.js 고정 버전을 검사하고 실행기록 보관 환경값을 설정한 뒤 n8n을 시작한다. `n8n start`, `n8n.cmd start` 등 직접 실행은 보관 설정을 적용하지 않으므로 사용하지 않는다.
- 포트 5678에서 이미 n8n이 실행 중이면 실행 중인 콘솔에서 `Ctrl+C` 등 정상 종료 절차로 먼저 멈춘 다음 전용 스크립트를 실행한다. 스크립트는 기존 프로세스를 강제 종료하지 않는다.
- `-CheckOnly`는 버전·포트·다음 시작 설정만 검사하며, n8n을 시작하거나 실행 중인 프로세스 설정을 바꾸지 않는다.
- 시작 후 `http://127.0.0.1:5678`이 응답하는지 확인한다. 보관값을 바꾸거나 확인해야 하면 정상 종료 후 전용 스크립트를 다시 실행한다.

## 분석기 시작 및 상태 확인

프로젝트 폴더에서 PowerShell로 실행한다.

```powershell
.\scripts\start_analyzer.ps1
```

PowerShell 창을 열어 둬야 로컬 n8n이 분석기를 호출할 수 있다. 재부팅 뒤에는 n8n과 분석기를 각각 다시 실행한다. health 확인:

```powershell
Invoke-RestMethod http://127.0.0.1:8765/health
```

응답의 `status`가 `ready`, `category_count`가 `247`, `abc_status`가 `owner_approved`, `taxonomy_version`이 현행 v3인지 확인한다. `not_ready` 또는 다른 버전이면 workflow를 실행하지 않는다.

## 주문 주소 분석 실행

1. `http://127.0.0.1:5678`에서 V1 workflow **공백상권 분석 V1 - 247개 업종**을 연다.
2. Analysis Input 노드에 해당 주문 주소를 입력한다. 공유용 workflow의 placeholder를 그대로 실행하면 주소 검증에서 중단된다.
3. Manual Trigger부터 전체 workflow를 실행한다. Kakao 주소 조회와 좌표 검증, analyzer 요청이 이어진다.
4. 결과를 전달하기 전에 Kakao와 analyzer의 HTTP 200, 정상 좌표 1건, 카테고리 247개, 전체 TOP20 20개, A TOP10 10개, 미분류 0개, publication gate `passed`를 확인한다.
5. 조회 실패나 gate 실패면 결과 파일을 전달하지 않고 주소·데이터·실행 상태를 확인한다. 오류를 0개 결과로 바꾸지 않는다.
6. 실행이 성공하거나 실패하면 즉시 Analysis Input의 주소를 정확히 `주소를 여기에 입력하세요`로 복원한다. 저장 후 노드를 다시 열어 placeholder인지 확인한다. 실패 실행도 주소를 담은 n8n SQLite 기록에 남을 수 있으므로 입력란 복원을 미루지 않는다.
7. 성공한 execution ID를 확인하고 먼저 읽기 전용 검사를 한다.

   ```powershell
   $python = '.\.venv\Scripts\python.exe'
   & $python scripts\deliver_from_n8n_execution.py --execution-id <실행ID> --check-only
   ```

   `publication_gate=passed`, category 247, TOP20 20, A TOP10 10, total 5km 수치를 확인한다. 통과하면 다음 명령으로 PDF/XLSX를 만든다.

   ```powershell
   & $python scripts\deliver_from_n8n_execution.py --execution-id <실행ID>
   ```

   결과는 `%LOCALAPPDATA%\GapAnalysis\deliveries\<request_id>`에 생성된다. 스크립트가 PDF 2페이지, 주소 포함, XLSX 시트명·247개 업종 행·주소 포함, manifest·파일 크기·SHA-256을 검사한다. 이후 출력된 절대 경로를 열어 PDF와 XLSX의 주소·기준일·분류표 버전·수치를 사람이 마지막으로 확인한 뒤 크몽 주문에 전달한다. 이 exporter는 운영자가 실행하는 별도 CLI이며 현재 n8n 노드에 연결되지는 않았다.
8. 고객 전달 전 workflow의 Analysis Input을 다시 열어 정확히 `주소를 여기에 입력하세요`인지 확인한다. placeholder가 아니면 전달을 보류하고 먼저 복원한다. 고객 전달일·삭제 예정일(전달일+30일)을 `운영/30일_보관_삭제_대장.csv`에 기록하고 상태를 `보관중`으로 둔다. 주소나 연락처는 적지 않는다. 만료일에 n8n UI에서 해당 execution을 삭제한 뒤 `python scripts\expire_deliveries.py`로 dry-run한다. 삭제 대상이 맞으면 `python scripts\expire_deliveries.py --apply`를 실행한다. 이 도구는 n8n DB에 execution이 남아 있으면 파일 삭제를 막고, execution이 없고 폴더 삭제까지 검증되면 날짜와 `삭제완료`를 대장에 쓴다. 2026-10-01에 가짜 주문·격리 SQLite로 만료일, 실행기록 보존 시 차단, 실행기록 제거 후 납품 파일 세 개 삭제, 대장 완료 표시까지 리허설했다. 실제 고객 주문 데이터는 사용하지 않았다.

실행 시 로컬 Python 분석기가 꺼져 있으면 n8n은 `127.0.0.1:8765`에 연결할 수 없다. 기본 설정은 **Windows 네이티브 n8n**이다. Docker 안에서 n8n이 실행 중이면 컨테이너의 `127.0.0.1`은 Windows 호스트를 가리키지 않으므로, 컨테이너 네트워크에 맞는 analyzer 주소를 별도로 설정해야 한다.

## 보안·데이터 경계

- Kakao Local API: 주소를 좌표로 바꾸는 데만 사용한다.
- 소상공인시장진흥공단 전국 CSV: 점포 공급 분석의 원자료다. 주문마다 외부 점포 API를 호출하지 않는다.
- SGIS: 현재 V1에서 호출하지 않는다.
- 두 credential은 n8n credential 저장소에서 따로 보관하며, workflow export JSON·CSV·리포트·채팅에 secret을 넣지 않는다.
- 입력 주소는 Kakao Local API에 전달되므로 주문 전에 고객에게 알린다. 사용자가 선택한 정책은 당사가 보유하는 분석 주소·n8n 실행기록·내부 납품물 사본을 결과 전달 후 30일 보관 뒤 삭제, 분석 시작 전 주소 수정 가능이다.
- Analysis Input 값은 workflow 설정에 저장되고 실행 데이터는 로컬 SQLite에 남는다. 고객 주소 처리 후 입력란을 placeholder로 복원한다. 주소가 표시된 내부 PDF/XLSX 사본도 결과 전달 후 30일 삭제 대상에 포함한다.
- n8n 공식 문서상 실행기록 자동 pruning 기본값은 336시간(14일)이며, 기본 최대 보관 건수 10,000건 기준으로도 오래된 실행이 먼저 삭제될 수 있다. 이는 설치별 실제 적용값이 확인됐다는 뜻이 아니다. [실행 데이터 관리 문서](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/manage-execution-data/)
- `scripts/start_n8n_with_retention.ps1 -CheckOnly`에서 Node.js 24.21.0/n8n 2.40.7 핀과 실행 중인 포트를 확인했다. 37.5일 pruning은 실행 시작 기준의 자동 정리 여유기간이며 고객 전달 후 정확히 30일에 맞춘 정리가 아니다. 정확한 만료일은 전달일 기준 삭제대장에서 수동 관리한다.
- 실행기록 목록에서 execution 271의 개별 `Delete` 메뉴가 보이는 것까지 확인했다. 기록 삭제 자체는 실행하지 않았다. 실제 삭제 후 목록에서 사라지는지 확인은 미완료다.
- 전달일 기준 삭제를 추적하려면 `운영/30일_보관_삭제_대장.csv`에 분석번호·실행 ID·전달일·삭제 예정일·삭제 확인일·상태만 적는다. 주소·고객 연락처는 이 대장에 적지 않는다. 실제 고객 execution/file 삭제는 아직 수행하지 않았으며, 해당 순서는 격리된 가짜 주문으로만 검증했다.
