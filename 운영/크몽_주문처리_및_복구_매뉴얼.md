# 공백상권 V1 초보자용 주문 처리·장애 복구 매뉴얼

갱신일: 2026-10-17  
대상: 기존 공백상권 V1, 크몽 #840642 / 49,000원  
현재 검증: 공개 시설 모의 주문 실행 #295 성공. 실제 유료 주문·고객 납품은 아직 하지 않음.

## 주문 처리에서 할 일 네 가지

1. 고객에게 분석 주소와 기준점을 확인한다.
2. 기존 n8n에서 주소를 넣고 V1을 수동 실행한다.
3. 성공한 실행 ID로 PDF·XLSX를 만들고 확인한다.
4. PDF와 XLSX만 크몽 주문 메시지에 전달한다.

## 1. 고객에게 받을 정보

- 국내 분석 주소 1곳.
- 도로명 주소가 넓거나 건물이 여러 개인 경우, 건물명·출입구 등 기준점을 추가로 확인한다.
- 고객 이름·전화번호·사업자번호 등 분석에 필요하지 않은 개인정보는 별도로 받거나 분석 기록에 적지 않는다.
- 주소는 Kakao Local API의 좌표 변환에 전달된다. 주문 전에 고객에게 이 처리와 분석 범위를 안내한다.
- 입력 주소·좌표는 n8n 실행 기록과 납품 파일에 남을 수 있으며, 결과 파일은 로컬 납품 폴더에 저장된다. 주소가 들어간 실행 기록/파일을 메신저·GitHub·공용 폴더로 옮기지 않는다.
- 분석 자료는 2026-06-30 기준 전국 상가 공공데이터다. 반경 1~5km의 점포 수와 공급 희소 순위를 보여준다. 수요·매출·임대료·창업 성공 가능성을 예측하지 않는다.

고객에게 보낼 안내 예시:

> 분석할 국내 주소 1곳과, 주소가 넓거나 건물이 여러 개인 경우 기준점을 보내주세요. 주소는 Kakao Local API의 좌표 변환에 사용됩니다. 결과는 2026-06-30 기준 공공데이터의 247개 업종 점포 공급 현황이며, 매출·수요·창업 성공을 예측하지 않습니다.

## 2. 주소 입력과 V1 실행

1. 이미 사용 중인 브라우저에서 `http://localhost:5678`을 연다. 새 n8n을 설치하거나 다른 포트를 열지 않는다.
2. `공백상권 분석 V1 - 247개 업종`을 연다. V1은 비활성 상태로 유지하고, `Execute workflow`로 수동 실행한다.
3. `Analysis Input` 노드를 열고 `address` 값에 고객 주소를 넣는다. `request_id` 식은 바꾸지 않는다.
4. `Execute workflow`를 누른다. 실행 목록의 성공한 execution ID를 주문 처리 기록에 적는다.
5. 아래 조건이 모두 맞는지 본다.
   - 7개 노드가 모두 성공 표시.
   - Kakao 주소 검색 HTTP 200, 일치 좌표 1건.
   - 분석기 HTTP 200, 업종 247개, 미분류 0개.
   - 전체 TOP20 20행, A 업종 TOP10 10행.
   - `publication_gate`가 `passed`.
6. `Analysis Input` 주소를 `주소를 여기에 입력하세요`로 되돌리고 노드를 다시 열어 저장값을 확인한다. 워크플로를 Publish/Activate 하지 않는다.

**중단 기준:** 주소 검색 결과가 0건/복수 건이거나 좌표가 맞지 않으면 고객에게 주소를 다시 확인한다. 노드 실패, HTTP 오류, 미분류 업종, 행 수 불일치, 게이트 실패가 하나라도 있으면 결과 파일을 만들거나 고객에게 보내지 않는다.

## 3. PDF·XLSX 생성과 확인

프로젝트 폴더에서 PowerShell을 열고, 성공한 execution ID를 넣어 먼저 읽기 전용 검사를 한다. 아래 Python 경로가 없으면 다른 Python으로 바꾸지 말고 관리자에게 문의한다.

```powershell
$py = Join-Path $env:USERPROFILE '.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe'
if (-not (Test-Path -LiteralPath $py)) { throw '공백상권 Python 3.12.14 실행 파일을 찾지 못했습니다.' }
$executionId = Read-Host '성공한 n8n execution ID'
& $py '.\scripts\deliver_from_n8n_execution.py' --execution-id $executionId --check-only
if ($LASTEXITCODE -ne 0) { throw '검증 실패: 납품 파일을 만들거나 보내지 마세요.' }
```

검사 결과가 `status=validated`, HTTP 200/200, `publication_gate=passed`, 업종 247, TOP20 20, A TOP10 10일 때만 파일을 생성한다.

```powershell
& $py '.\scripts\deliver_from_n8n_execution.py' --execution-id $executionId
if ($LASTEXITCODE -ne 0) { throw '파일 생성 실패: 고객에게 보내지 마세요.' }
```

기본 저장 위치는 `%LOCALAPPDATA%\GapAnalysis\deliveries\<GAP-요청번호>`다. 생성 결과의 `output_dir`을 열어 다음을 확인한다.

- PDF가 정확히 2페이지이고 글자·표·숫자·한글이 잘리지 않는다.
- XLSX가 열리고 `요약`, `전체 247개` 시트가 보인다. 전체 시트에 업종 247개가 있고 요약 TOP20/A TOP10이 상세표와 일치한다.
- 주소와 기준일 `2026-06-30`, 반경별 수치가 주문 요청과 실행 결과에 맞다.
- `manifest.json`의 두 파일 크기와 SHA-256이 실제 파일과 일치한다.

확인이 끝나면 고객에게 PDF와 XLSX 두 파일만 전달한다. `manifest.json`, 실행 데이터베이스, 원본 CSV/SQLite, 토큰/credential은 전달하지 않는다.

## 오류가 날 때

| 상황 | 조치 |
|---|---|
| 주소 검색 0건 또는 여러 건 | 주소/건물 기준점을 고객에게 재확인한다. 다시 분석하기 전 좌표 1건인지 확인한다. |
| Kakao 또는 분석기 인증·연결 오류 | 고객 납품을 중단한다. credential이나 토큰을 초기화·재생성하지 말고 관리자에게 로그의 민감정보를 가린 뒤 문의한다. |
| n8n 또는 분석기 주소가 응답하지 않음 | 기존 서비스를 종료하거나 새 인스턴스를 만들지 않는다. `start_analyzer.ps1`은 토큰 파일이 없으면 새 토큰을 생성할 수 있으므로 임의로 실행하지 않는다. |
| 게이트 실패, 행 수/기준일 불일치 | PDF/XLSX를 생성하거나 전달하지 않는다. 실패 execution ID와 오류 노드만 기록한다. 주소·응답 본문은 공유하지 않는다. |
| PDF/XLSX 누락, 깨짐, 해시 불일치 | 두 파일 모두 전달하지 않고 생성 폴더를 보존한 채 관리자에게 문의한다. |
| 백업 복원이 필요함 | 운영 `.n8n` DB를 백업 파일로 덮어쓰지 않는다. 격리 복원과 관리자 검토를 거친다. |

## 주소·결과 보관과 30일 삭제

- `운영/30일_보관_삭제_대장.csv`에는 분석번호, n8n 실행 ID, 납품 폴더 ID, 고객 전달일, 전달일+30일 삭제 예정일, 삭제 확인일, 상태만 기록한다. 주소·이름·전화번호는 적지 않는다.
- 현재 대장은 헤더만 있고 주문 행은 0건이다.
- 격리된 가짜 주문으로 `scripts/expire_deliveries.py`의 미리보기와 삭제 동작을 시험했다. 이 스크립트는 n8n 실행 기록을 삭제하지 않는다. 연결된 실행 기록이 남아 있으면 `delete_n8n_execution_first`로 파일 삭제를 막는다.
- 실제 주문은 만료일에 대상 실행 ID를 확인하고, 운영 정책에 따라 해당 n8n 실행 기록을 먼저 정리한 뒤 스크립트를 기본 미리보기로 실행한다. 결과가 해당 주문에 대해 `would_delete_files`로 확인될 때만 `--apply`로 납품 폴더를 지우고 대장을 갱신한다. 다른 실행 ID/폴더는 선택하거나 지우지 않는다.
- **정확히 전달 30일 뒤 자동 삭제가 구현된 상태는 아니다.** 실행 중 n8n의 자동 정리 환경값은 읽기 전용 점검으로 확인되지 않았다. 기존 `scripts/start_n8n_with_retention.ps1`은 다음 실행에서 900시간 보존을 설정하지만, 현재 서비스를 재시작하지 않고 적용 여부도 확인하지 않았다. 따라서 실제 삭제 시점을 보장하지 말고, 이 절차를 운영자가 확인해야 한다.

## 백업 복구 — 관리자 전용

- 보호된 로컬 백업은 프로젝트의 `data/backups/n8n-ops-recovery-20261017/`에 있다. n8n DB 스냅샷은 SQLite 무결성 `ok`로 확인했고, 격리 복사본의 DB·설정·워크플로 접근을 검사했다.
- 백업의 n8n 설정 파일에는 암호화 키가 포함될 수 있다. 해당 폴더를 외부 저장소·GitHub·메신저로 복사하지 않는다.
- 격리된 n8n CLI 내보내기가 응답 없이 멈춰 전체 n8n 재기동·credential 복호화까지 복구 검증한 것은 아니다. 복원 테스트를 운영 DB에 적용하지 않는다.
- 장애 시 사용자가 할 일은 오류 화면과 시간만 기록하고 중단하는 것이다. DB/WAL/SHM, 설정, 키, credentials를 삭제·덮어쓰거나 서비스를 반복 재시작하지 말고 관리자에게 요청한다.
